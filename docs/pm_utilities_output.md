# Utilities capture and Output

The existing capture pages retain their entry fields and validation. View Meter and View Account filter historical rows locally by registered database ID; they never post or change data. All Meters and All Accounts restore the date-descending display. Output preserves the property, source and selected item; Back returns to that source with the filter selected.

The shared authenticated route is /billing/utilities/<property_id>/output. Its GET preview accepts source=readings or reconciliation, item_id (blank means all authorised items), date_from and date_to. Dates are inclusive; either boundary may be omitted. The server independently verifies property access and that any selected item belongs to that property. Preview displays only stored records, including their original values and dates. Amount Paid reuses existing municipal-account/billing-period payment attribution; it is Unavailable when the allocation source is absent. No tenant-ledger or property-wide payment totals are substituted.

Print uses the report-only browser print layout. Email opens an inline recipient form prefilled from the authenticated user's email, when available. The user may enter a valid destination and must click Send PDF. A CSRF-protected POST validates a signed, user/property/filter-bound preview token and rejects stale data before generating the attachment and calling the existing app.utils.mailer.send_pdf_email helper. GET requests never send mail. Successful sends redirect back to preview with an in-tile flash; validation, PDF and delivery failures show clear errors. Preview tokens expire after 30 minutes. No report is stored on disk by the application.

PDF rendering reuses app.utils.pdf_render.html_to_pdf_bytes: the existing WeasyPrint installation on Linux, or the configured wkhtmltopdf executable (WKHTMLTOPDF_EXE/default installation) as supported by that helper. Email depends on the existing Flask-Mail MAIL_* configuration and default sender. The application's existing SECRET_KEY signs preview tokens. No new credentials, variables, tables or migrations are introduced. Isolated tests mock email delivery; no live messages or production records were created. Render deployment and live SMTP/PDF configuration require separate production verification.
