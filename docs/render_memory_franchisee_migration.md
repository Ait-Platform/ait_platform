## Findings and limits

### Production evidence supplied by the operator

- Cgroup consumption: 490.78 MiB of 512 MiB; only 21.22 MiB of snapshot headroom.
- Master plus worker **PSS**, not summed RSS: 349.11 MiB. Their Private Dirty totals 61.79 MiB; each reports 245.91 MiB Shared Dirty. Those shared pages must not be counted twice as private memory.
- About 141.68 MiB is not explained by those two PSS figures. Cgroup file cache, kernel accounting and other processes require inspection; this subtraction does not identify a leak.
- The shown Gunicorn command alone does not explain the large master heap. Gunicorn 23 defaults `preload_app=False`; environment arguments or a config file can override it. The installed source imports the WSGI app in the master when preload is enabled. **Effective production preload configuration and the precise cause of the 491 MiB total are unconfirmed.** Do not change preload blindly, because it affects sharing.

### Confirmed startup/import paths

- Importing `app.extensions` first executes `app/__init__.py`. That package imports pricing/Reading routes, model registrations, config and Matplotlib/NumPy. The normal factory then registers all programme blueprints, including Admin, PM, Loss, ProTrade, SACE, UIP and Retirement.
- The full factory eagerly loads/attempts reporting/PDF libraries (WeasyPrint, ReportLab, xhtml2pdf), even without rendering a document. These paths were not changed. No PDF was generated by the memory probe. This is **not evidence that the prior PDF peak-memory problem has returned**.
- Admin Hub imported `google.genai` without using it. The Grade 12 scan module also imported it at registration, although only its on-demand AI scan uses it. The unused import is removed and the other is deferred until that scan needs it. SDK calls and PDF handling are otherwise unchanged. Cached and validation paths do not load the SDK.
- `create_app()` defaults to normal boot maintenance: automatic migration attempts, multiple DDL repairs, subject visibility updates and a view replacement. `SKIP_AUTO_MIGRATE` does not guard all of these. The existing **`wsgi:app`** entry point calls `create_app(operator_mode=True)` and skips those startup mutations; this was verified locally with writes forbidden.
- `flask db ...` loads a Flask application. Whether the failed production CLI used default `create_app()` or operator-mode WSGI depends on production `FLASK_APP`/auto-discovery, which was not supplied. Either path loads the web application. The initial migration delay is **unconfirmed**: no production lock/wait trace or command timing is available.
- Independently, `flask db upgrade ait_franchisee_001` as written does not supply the revision's required approval attribute. It cannot successfully apply this migration once it reaches that guard. The guard is preserved.
- The old standalone Alembic environment imported `app.extensions` and `app.models` too. An opt-in `Config.attributes['skip_app_metadata']=True` now avoids those imports for operational commands. ORM metadata is unnecessary for executing existing revision declarations. Default metadata/autogeneration behavior is preserved; do not use this flag for autogeneration/check workflows.
- None of the 86 revision files has a top-level AIT/heavy-library import. The lightweight `current` path was verified in a fresh subprocess to load no AIT or heavy-library family.
- `migrations/alembic.ini` incorrectly resolved `%(here)s/migrations` to a nested migrations directory when used directly. It now uses `%(here)s`. Flask-Migrate previously overrode this path, so this is **not established as the cause of the production delay**.

## Exact approved pre-deploy command

This uses standard Alembic `Config`/`command.upgrade` and the existing SQLAlchemy URL. It is not a replacement DDL/version runner. Only Alembic records the revision. The **outer transaction includes DDL and revision updates**, with bounded connection/lock/statement waits. Order: **`protrade_trade_codes_019` → `ait_franchisee_001`**. Every other current head must remain unchanged. The procedure is stored in `scripts/apply_franchisee_migration.py` so Render can use a single-line command without heredoc parsing.

**Do not execute before explicit production migration approval.**

<!-- MIGRATION_COMMAND -->
```sh
python scripts/verify_franchisee_environment.py && python scripts/apply_franchisee_migration.py
```
<!-- END_MIGRATION_COMMAND -->

If the transaction fails before commit, PostgreSQL rolls back its DDL/version changes. If the connection is lost during commit, the outcome may be uncertain: verify first. Do not drop partial-looking objects, stamp revisions, delete version rows, retry repeatedly, or run concurrent migration commands. A missing parent, unexpected existing object or changed head set stops this procedure without a repair attempt. Lock/statement timeouts stop an unbounded wait; SQLSTATE is reported without credentials, SQL parameters or exception contents.

## Exact PostgreSQL verification

Run in the approved database console, or in a separate execution instance with `psql` available, using the current connection. It is read-only and does not reveal passwords or franchisee data:

```sh
psql "$DATABASE_URL" -X -v ON_ERROR_STOP=1 -c "BEGIN READ ONLY; SET LOCAL statement_timeout='10s'; SELECT current_database(), current_user; SELECT version_num FROM alembic_version ORDER BY version_num; SELECT to_regclass('ait_franchisee_registration') AS registration_table, to_regclass('ait_franchisee_number_seq') AS number_sequence; SELECT conname, contype FROM pg_constraint WHERE conrelid=to_regclass('ait_franchisee_registration') ORDER BY conname; COMMIT;"
```

Before migration: parent 019 is current, new target absent, both franchisee objects absent. After migration: new target replaces only parent 019, other heads are identical, both objects exist and their constraints are present. If `psql` is unavailable, the Alembic pre-deploy command already performs the head/object verification within its transaction; use a trusted PostgreSQL client for the standalone query rather than starting a full Flask process. Never manually edit `alembic_version`.

## Verification performed

The approved local role lacks CREATE DATABASE and CREATE SCHEMA. The operator explicitly approved disposable **session-temporary objects** instead. The real Alembic environment, graph, target revision, sequence, constraints and revision updates were tested there; temporary-relation checks prevent accidental use of public production-like tables. Test baselines were established with Alembic's framework stamp only in that disposable fixture; stamping is **not** part of the production procedure.

Tests cover all repository heads preserved, parent dependency, approval refusal, target re-run as a no-op, forced failure immediately before version update rolling back both new objects, default metadata mode still present, fresh-process no-AIT imports, Fernet/origin validation without secret output, real read-only factory/route registration, existing Admin Hub guard/template, and deferred/cached scan behavior. Registration, encryption and ProTrade output regressions are also run. The documented command is separately exercised against the temporary fixture.

Final focused suite: **35 tests and 5 subtests passed**, no failures/skips. The separate existing `test_home_operator_startup.py` real-factory/CLI test also passed: **36 tests total**. Compilation and patch-format checks passed. No test connects to production; database/schema creation was not attempted after the local privilege check and the operator's temporary-object decision.

Windows cannot run Gunicorn's Linux fork/process model; actual Render post-release PSS/cgroup behavior remains a live check. The existing Windows factory test emits WeasyPrint native-library warnings, but passes with no startup mutations; the PDF implementation was not changed or diagnosed as regressed.
