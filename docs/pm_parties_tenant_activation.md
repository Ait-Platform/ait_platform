# Tenant and representative completion

## Runtime

The two temporary owner/structured-lease environment gates have been removed from runtime code and configuration. Neither is needed in Render. No replacement switch was introduced. Existing login, active-user checks on lease routes, manager/property authorization, validation, schema checks, ownership-history triggers, optimistic draft versions and transactional commits remain. Separate legacy upload/private-storage gates remain unchanged.

The single main register is now `bil_tenant`: name, party_type, identity_number, address, email, phone and manager_id. Registration reads/writes explicit columns only after the final tenant schema is available. It supports both initial schema variants and the migration ensures both distinct nullable relationships exist afterward. Standalone registration does not create a unit. An optional explicit assignment uses the selected authorized property and an actual unit belonging to it; no artificial units are created. METSOA fields, foreign keys and existing billing code remain. The three new ORM fields are deferred, so existing billing queries do not start selecting missing columns before SQL rollout; the new register itself remains schema-gated.

`bil_tenant_identity` now represents a tenant's representative via tenant_id. It reuses legal_name, identity_number, phone and email. Natural persons have no representative row. Juristic tenants require a representative's name, ID, telephone and email, saved atomically with their tenant. No capacity input is required or invented. Old signatory/identity columns are retained nullable and obsolete check requirements removed, rather than dropping records or columns. The existing-table constraint permits one current representative per tenant.

Selected tenant_id and representative_id, identities and contact details are snapshotted in lease draft JSON. Historical snapshots and generated-document values remain unchanged. Old tenant_identity_id values are not guessed to be new tenant IDs. Old drafts remain readable/generatable; select a registered bil_tenant when resaving Parties. Master, merge tokens and Parts B-E remain unchanged.

## Safeguards and limits

No production SQL was executed by this work package. Production schema compatibility is not inferred from local tests: the production column/constraint inventory still must be compared with the preflight output. Existing table definitions are not overwritten; collisions and unexpected foundations cause the transaction to fail. A rollback on an error preserves both schema and Alembic branch state. An automatic downgrade is deliberately refused once this table's meaning is changed; restore/reversal needs a separate reviewed plan.

Essential local tests cover both tenant schema variants, natural/juristic representation and visibility, atomic rollback, owner saving without switches, tenant selection and duplicate reuse, lease save/reopen and other-section preservation, unauthorized requests, and Word generation for both party types with no stale representative data. These tests use disposable PostgreSQL; they do not establish Render operation or end-to-end METSOA/SACE/HOME/UIP verification.

## Final property/unit compatibility and remaining METSOA limit

property_id identifies the property; sectional_unit_id identifies a particular unit within it. Both remain distinct and nullable. Existing foreign keys are checked and preserved. A missing property_id or sectional_unit_id is added with the correct foreign key, compatible existing address is preserved, and missing address becomes VARCHAR(500). A tenant insert/update trigger validates that an assigned unit belongs to the supplied property, holding a shared unit lock during validation. The new register validates manager authorization and the same relationship server-side. Reusing an existing identity does not silently change its assignment.

The existing ORM already maps both relationships nullable, so this correction needs no model rewrite. The existing property owner and lease draft remain separate records. No METSOA calculation, meter assignment, operational lease or document schema changes are included.

METSOA limitation remains OUT OF SCOPE: tenant-specific helpers in app/utils/billing_helpers.py use tenant.property_id without an explicit unassigned-tenant guard. A NULL value may match unassigned meters. Older billing_map/billing_metsoa_builder queries also contain inconsistent property aliases. Adding property_id fixes the missing-column foundation but does not establish correct billing for unassigned or multi-unit tenants. Do not use a tenant without verified meter/unit allocation for tenant-specific billing. The ORM also still maps date_started/date_terminated/is_active, absent from the administrator-reported tenant inventory; the new register uses explicit SQL columns and does not depend on those optional fields. These pre-existing billing compatibility issues remain outside this correction. This work does not claim production METSOA verification.

Final focused checks cover exact production columns, compatible local columns, preservation of original foreign keys and operational columns, standalone natural/juristic registration, two real units with separate tenants, invalid/unauthorized unit assignments, Save/Reopen, and Word generation without stale representatives. Only disposable PostgreSQL is used. The production migration and deployed application still need administrator verification together.
